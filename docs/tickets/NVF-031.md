# NVF-031: Improve NVF AI prompt workflow with mature plugin evaluation

## Summary

Analyze the current NVF AI prompt workflow and improve the in-editor experience by evaluating adoption of a mature plugin such as `avante.nvim` for Codex/OpenAI-compatible subscription-oriented workflows.

## Purpose

Provide a stronger interactive AI editing workflow without replacing the existing guarded Pi bridge that remains useful for orchestration and TUI-style tasks.

## Context

Phase 5 delivered a guarded NVF AI bridge that shells out to existing Claude, Codex, and Pi tooling with confirmation and redaction controls. That bridge is intentionally conservative, but the prompt workflow may be less capable than mature in-editor assistant plugins. This ticket tracks a post-roadmap follow-up to evaluate `avante.nvim` or a comparable mature plugin for OpenAI-compatible/Codex-oriented workflows while keeping Pi as a separate guarded orchestration path rather than forcing it into the same UX.

## Acceptance criteria

- [x] The current NVF AI prompt workflow in `home/modules/nvf/ai.nix` and related docs is reviewed, with concrete UX gaps and guardrail requirements recorded.
- [x] `avante.nvim` is evaluated as the preferred candidate, including NVF/Nix packaging feasibility, OpenAI-compatible provider support, Codex/subscription workflow compatibility, keymap ergonomics, context handling, and maintenance maturity.
- [x] A decision is documented to adopt `avante.nvim`, adopt a justified alternative, or defer plugin adoption with clear reasons and follow-up work.
- [x] If a plugin is adopted, it is integrated behind explicit NVF configuration with no committed credentials and no automatic full-buffer or repository-wide context sharing.
- [x] The existing guarded Pi bridge remains available as a distinct orchestration/TUI path, and any overlap with existing leader-a AI keymaps is documented or migrated without removing the guarded Pi workflow.
- [x] Documentation explains provider setup, expected subscription/API-token boundaries, privacy implications, and when to use the plugin workflow versus the Pi bridge.
- [x] Validation evidence covers NVF evaluation/build checks for affected Home Manager profiles plus a runtime Neovim smoke check or a documented reason if plugin runtime validation is deferred.

## Limitations

- CodeCompanion does not inherit the guarded bridge's redaction, sensitive-path blocking, confirmation summary, or full-buffer-selection guardrails.
- Runtime checks used a build-local NVF package rather than Home Manager activation.
- Normal-mode `<leader>aA` is intentionally unmapped; curated action-palette prompts are visual-mode only because they require an explicit selected range.
- Visual-mode CodeCompanion mappings rely on Neovim's automatic visual range; the Phase 7 script rejects regressions to duplicated explicit `:'<,'>` RHS forms.

## Follow-ups

- None for the NVF-031 visual mapping blocker. Future hardening should continue to treat CodeCompanion as separate from the guarded bridge and re-run Phase 7 validation when mappings or context controls change.
