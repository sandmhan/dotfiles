# RCA: e1000e NIC TX Ring Hang - 2026-05-03

## Summary

All VMs on the Dell Proxmox node became network-inaccessible for approximately 7 hours due to an Intel I217 (e1000e) NIC transmit descriptor ring hang. The hang was triggered by a burst of network traffic from concurrent wger ingredient sync operations on VM 106 (fitness). The Proxmox node itself remained online and all VMs continued running, but no network traffic could traverse the bridge.

## Impact

- **Duration**: ~7 hours (2026-05-02 23:41 EDT to 2026-05-03 06:27 EDT)
- **Affected systems**: All VMs on the Dell Proxmox node (VM 102 matrix, VM 105 agent-sandbox, VM 106 fitness, VM 110 tailscale-router, LXC 207 lxc-monitor)
- **Severity**: Full network outage for all hosted services
- **Resolution**: Manual reboot by user after noticing network was down

## Root Cause

### Direct cause

The Intel I217 NIC (e1000e driver, PCI Express 2.5GT/s x1) experienced a hardware transmit unit hang. The TX descriptor ring became stuck: the head pointer (TDH) could not advance to process queued transmit descriptors, while the tail pointer (TDT) continued to accept new packets from the kernel. This is a known hardware bug in Ivy Bridge-era Intel I217 LOM chipsets.

### Trigger

A burst of outbound network traffic caused by concurrent ingredient sync operations on the wger (fitness) VM:

1. **Celery auto-sync** (`SYNC_INGREDIENTS_CELERY = "True"`) was actively running, fetching ingredients from the Open Food Facts API and performing bulk PostgreSQL inserts
2. **Manual sync** (`podman exec wger python3 manage.py sync-ingredients`) was triggered at 23:40:24, downloading the bulk ingredient dump from `wger.de/media/ingredients/ingredients.jsonl.gz` concurrently
3. The combined traffic (HTTPS downloads from wger.de/OFF, TCP ACKs, bridged inter-container traffic, PostgreSQL WAL writes generating disk I/O interrupts) exceeded the NIC's TX ring capacity

### Contributing factors

- **No swap configured** on the Dell Proxmox node - memory pressure from 6 running VMs (total allocated: ~14.3 GB of 15 GB RAM) leaves no headroom
- **Single NIC** (Intel I217 LOM) - no redundancy, single point of failure for all VM network access
- **e1000e driver lacks automatic TX reset** - once the TX ring hangs, the driver logs warnings but does not attempt a hardware reset or ring reinitialize
- **Watchdog response time** - the software watchdog took ~7 hours to trigger a reboot, suggesting the watchdog was being kept alive by non-network-dependent activity on the host
- **No network health monitoring** - no automated check that detects NIC TX hangs and triggers a driver reload (`modprobe -r e1000e && modprobe e1000e`)
- **Polling script** - repeated `/api/v2/ingredient/?format=json&limit=1` requests every ~2 minutes added steady-state outbound traffic during the sync window

## Kernel diagnostics

From the hang messages:
```
e1000e 0000:00:19.0 eno1: Detected Hardware Unit Hang:
  TDH                  <98>        # TX descriptor head - frozen
  TDT                  <b1>        # TX descriptor tail - 25 descriptors queued
  next_to_use          <b1>
  next_to_clean        <97>
  time_stamp           <129a28426> # frozen - descriptor not being processed
  next_to_watch.status <0>         # hardware has not completed the descriptor
  MAC Status           <80083>     # link up, TX paused
  PHY Status           <796d>      # link 1000Mbps, full duplex
  PCI Status           <10>        # no PCI errors
```

The MAC Status `0x80083` indicates: link up (bit 1), speed 1000 (bits 6-7), but the transmit function is paused/stuck. The PHY confirms physical link is healthy at 1 Gbps. This is purely a MAC-level TX engine failure.

## Remediation

### Immediate (done)

- Manual reboot of the Proxmox node at 06:27, restoring all services

### Short-term

1. **[DONE] e1000e watchdog script deployed** - A systemd timer (`e1000e-watchdog.timer`) runs every 30 seconds on the Proxmox host, checking `dmesg`/`journalctl` for recent "Hardware Unit Hang" messages. On detection it attempts a two-stage recovery:
   - Stage 1: Soft reset (`ip link set eno1 down/up`)
   - Stage 2: Module reload (`modprobe -r e1000e && modprobe e1000e`) with bridge re-add
   - Rate-limited to 3 recoveries per hour via `/tmp/e1000e-watchdog.state`
   - All actions logged to syslog under tag `e1000e-watchdog`
   - Source: `scripts/e1000e-watchdog.sh`, `.service`, `.timer` in the dotfiles repo
   - **Note**: This is a bandaid, not a fix. The underlying hardware limitation remains. The watchdog reduces outage duration from hours to ~30-40 seconds but cannot prevent the hang from occurring.

2. **Disable concurrent ingredient syncs** - Remove `SYNC_INGREDIENTS_CELERY = "True"` or gate the manual sync-ingredients command to check if celery is already syncing. Only one sync path should be active at a time.

3. **Rate-limit wger sync network traffic** - Add `tc` traffic shaping or podman `--network` bandwidth limits to prevent the fitness VM from saturating the NIC TX queue.

### Long-term (recommended)

1. **Replace the Intel I217 NIC** - Add a USB 3.0 Ethernet adapter (e.g., Realtek RTL8153) or a PCIe NIC as a secondary interface. Bond or failover between the two.

2. **Enable swap on Proxmox** - Even 2-4 GB of swap provides a pressure relief valve during memory spikes from concurrent VM operations.

3. **Reduce VM memory overcommit** - Current allocation (14.3 GB across VMs) leaves only ~700 MB for the Proxmox host. Consider enabling memory ballooning (`qm set <vmid> --balloon <min>`) to reclaim unused RAM.

## Lessons learned

- The Intel I217 NIC on the Dell node is a recurring failure point (see also: [2026-04-24 agent qm loop crash](./2026-04-24-agent-qm-loop.md)). Any operation that generates sustained outbound traffic bursts risks triggering the TX hang.
- Running bulk data imports (ingredient sync, database migrations) on VMs should be scheduled during low-traffic windows and never run concurrently.
- The wger module's `SYNC_INGREDIENTS_CELERY = "True"` setting creates a background sync path that isn't visible when manually triggering syncs, leading to accidental concurrency.
